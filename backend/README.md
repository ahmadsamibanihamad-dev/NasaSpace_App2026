# خادم أرضنا (Backend)

FastAPI مع SQLite. يخدم نوعين من المستخدمين:

- **الضيف**: يحدد موقعاً ويحصل على المحاصيل المقترحة. لا حساب، لا مزرعة، ولا شيء يُحفظ.
- **المستخدم المسجّل**: مزارعه وقطعه وسجل محاصيله وتحليلاته وتوقعاته محفوظة له، ولا يراها غيره.

> **الحالة:** الخادم مكتمل ومختبر (61 اختباراً) والموقع مربوط به عبر `frontend/src/lib/data/repo.ts`. المنفذ 8765.

## التشغيل على Windows

انقر نقراً مزدوجاً على `start-backend.bat` في المجلد الرئيسي. يُنشئ بيئة Python في أول مرة، ثم يشغّل الخادم.

أو يدوياً من داخل `backend/`:

```bash
python -m venv .venv
```

```bash
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

```bash
.venv\Scripts\python.exe -m uvicorn app.main:app --port 8765
```

- الخادم: <http://localhost:8765>
- توثيق تفاعلي لكل الواجهات: <http://localhost:8765/api/v1/docs>
- الاختبارات: `.venv\Scripts\python.exe -m pytest -q`

قاعدة البيانات ملف `backend/ardna.db` يُنشأ تلقائياً عند أول تشغيل.

## الإعدادات

انسخ `.env.example` إلى `.env`. أهم القيم:

| المتغير | الوظيفة |
|---|---|
| `JWT_SECRET` | سر توقيع جلسات الدخول. إن تُرك فارغاً يُولَّد عشوائياً عند كل تشغيل، فيخرج الجميع عند إعادة التشغيل |
| `AI_MODE` | `off` (افتراضي) أو `mock` أو `production`. انظر «ربط النموذج» |
| `MODEL_DIR` | مجلد ملفات النماذج وسجلّها |
| `OFFLINE_MODE` | `true` يمنع الاتصال بالمصادر الخارجية ويستخدم المخزّن فقط |
| `RATE_LIMIT_AUTH` / `RATE_LIMIT_GUEST` | عدد الطلبات في الدقيقة لكل عميل |
| `CORS_ORIGINS` | عناوين الواجهة المسموح لها |

## الواجهات (`/api/v1`)

**بدون تسجيل دخول**

| الواجهة | الوظيفة |
|---|---|
| `POST /guest/recommendations` | موقع (واختيارياً توفر الري) ← المحاصيل المقترحة مرتبة. لا يُحفظ شيء |
| `GET /geo/locate` | هل النقطة داخل الأردن، وما محافظتها |
| `GET /crops`، `GET /crops/{id}` | قاعدة معرفة المحاصيل مع مصدر كل قيمة |
| `POST /auth/register`، `POST /auth/login`، `POST /auth/forgot-password` | الحسابات |
| `GET /health`، `GET /models/status`، `GET /data/status` | حالة النظام والنماذج وحداثة البيانات |

**تحتاج تسجيل دخول**

| الواجهة | الوظيفة |
|---|---|
| `GET/PATCH /auth/me` | بيانات المستخدم |
| `GET/POST /farms`، `GET/PATCH/DELETE /farms/{id}` | المزارع |
| `POST /farms/demo` | إنشاء المزرعة التجريبية (معلّمة `is_demo`) |
| `GET/POST /farms/{id}/plots`، `GET/PATCH/DELETE /plots/{id}` | القطع |
| `GET/PUT /plots/{id}/history` | سجل المحاصيل |
| `GET /environment/summary`، `GET /environment/timeseries` | ملخص البيئة والسلاسل الزمنية |
| `POST /analyses`، `GET /analyses`، `GET/DELETE /analyses/{id}` | التحليلات الستة وسجلّها |
| `GET /outlook/status`، `POST /outlook` | توقعات 30 و90 يوماً من حزمة فريق الذكاء مع ترتيب المحاصيل |
| `POST /forecasts`، `GET /forecasts/history`، `GET /forecasts/{id}` | طبقة التوقع القديمة (غير مستخدمة في الواجهة) |

الأخطاء كلها بصيغة واحدة: `{"error": {"code", "message", "details"}}`. أهم الرموز: `UNSUPPORTED_LOCATION`، `UNSUPPORTED_CROP`، `INVALID_GEOMETRY`، `DUPLICATE_LABEL`، `RATE_LIMITED`، `MODEL_UNAVAILABLE`، `FORECAST_DISABLED`.

## كيف تُحسب التوصية الآن

بدون نموذج (`AI_MODE=off`) تعتمد التوصية على سجل المناخ التاريخي من NASA POWER (12 سنة) مع قواعد شفافة:

- **الحرارة**: حدود المحصول من FAO ECOCROP مطبّقة على حرارة كل يوم في الموسم.
- **الماء**: نسبة تغطية المطر الفعّال لاحتياج المحصول المائي (FAO-56)، مع موثوقية المطر وأمطار فترة الإنبات. الري يلغي عقوبة نقص المطر.
- **رطوبة التربة والإشعاع**: نطاق عام.
- **الدرجة**: مجموع موزون، ثم قاعدة العامل المحدِّد، ثم خصم المخاطر.

الأوزان والعتبات في `app/data/engine_config.json` وتُعدَّل بدون تغيير الكود. المحاصيل ومتطلباتها في `app/data/crops.json`، وإضافة محصول جديد تعديل بيانات فقط.

المحرك نُقل من محرك كان داخل الواجهة ثم حُذف من هناك. ملف `tests/fixtures/parity.json` يحفظ نتائج ذلك المحرك كمرجع ثابت، واختبارات `test_engine_parity.py` تتأكد أن محرك الخادم ما زال يعطي الأرقام نفسها. إذا غيّرت قاعدة عن قصد فحدّث القيم المرجعية في الملف مع التغيير.

## توقعات فريق الذكاء الاصطناعي (`/outlook`)

حزمة الفريق `NASA_FINAL` منسوخة كما هي في `backend/nasa_final/` بدون تعديل على ملفاتها:

```
nasa_final/
  AI/recommendation_api.py      راوتر الفريق ودالة العرض التجريبي
  AI/recommendation_system.py   قواعد ترتيب المحاصيل
  AI/crop_requirements.json     المحاصيل الستة ونطاقاتها
  AI/forecasting/               النماذج المحفوظة، سجل النماذج، صيغ خط الأساس
  data/demo/                    خصائص تاريخية جاهزة لـ835 نقطة شبكية (تاريخ الأصل 2026-05-01)
  data/processed/               جدول خصائص التربة (SoilGrids)
```

`app/api/outlook.py` يستدعي دوال الفريق ويضيف ما يلزم الموقع: التحقق من حدود الأردن، تحديد عدد الطلبات، صيغة الأخطاء الموحدة، حموضة التربة من جدول الفريق، والنص الإنجليزي بجانب العربي.

| الواجهة | الوظيفة |
|---|---|
| `GET /outlook/status` | هل الحزمة جاهزة، تاريخ الأصل، والمحاصيل الستة |
| `POST /outlook` | موقع (ومعلومة الري وحموضة التربة اختيارياً) ← توقع 30 و90 يوماً للحرارة والرطوبة ورطوبة سطح التربة والأمطار، وثلاثة محاصيل مرتبة لكل فترة مع الأسباب والتنبيهات. بدون حساب، ولا يُحفظ شيء |

ملاحظات:

- **الوضع الحالي عرض تجريبي تاريخي** (`data_mode: historical_demo`): التوقع محسوب من لقطة خصائص تاريخها 2026-05-01، وليس توقعاً حياً. الواجهة تذكر ذلك بوضوح.
- التوقع الحي يحتاج بناء الخصائص حسب الموقع والتاريخ من مصادر البيانات. لم يُبنَ بعد.
- من الأهداف الثمانية المستخدمة، واحد فقط نموذج مدرّب (حرارة 90 يوماً، XGBoost). السبعة الباقية صيغ خط أساس اختارها الفريق لأنها كانت الأدق في التحقق. الرد يذكر الطريقة ومتوسط الخطأ لكل قيمة.
- **إصدار xgboost:** النماذج دُرّبت بالإصدار 3.4.1 الذي يحتاج Python 3.12. البيئة هنا Python 3.11 مع xgboost 3.2، والنماذج تُحمَّل وتعمل دون تحذيرات، لكن تطابق الأرقام مع 3.4.1 لم يُتحقق منه.
- حموضة التربة: تُؤخذ من بيانات القطعة إن أدخلها المستخدم، وإلا من جدول الفريق لأقرب نقطة شبكية. إن لم تتوفر (5 نقاط من 835 فارغة) تُترك ولا تُخترع.
- طبقة `app/ml/` و`/forecasts` القديمة ما زالت موجودة لكنها غير مستخدمة في الواجهة.

## ربط النموذج (الطبقة القديمة)

النموذج يتوقع الظروف (الحرارة، الرطوبة، رطوبة التربة، المطر)، ثم **قواعد القرار** تحكم أي محصول يناسب تلك الظروف. الاثنان منفصلان.

**1. طبقة التوقع** (`app/ml/`): واجهة واحدة `PredictionService.predict(...)` بثلاثة تنفيذات يختار بينها `AI_MODE`:

| الوضع | السلوك |
|---|---|
| `off` | لا توقعات. `POST /forecasts` يرجع `FORECAST_DISABLED` |
| `mock` | بيانات توضيحية بنفس شكل الرد النهائي، معلّمة `data_mode: "mock"` مع تحذير |
| `production` | يحمّل النماذج الحقيقية مرة واحدة عند التشغيل. إذا نقص نموذج يرجع `MODEL_UNAVAILABLE` ولا يرجع أبداً لبيانات وهمية |

**2. سجل النماذج**: ملف JSON لكل نموذج في `MODEL_DIR/manifests/`. الحقول والمثال في أعلى `app/ml/production.py`.

**3. قواعد القرار** (`app/engine/decision.py`): تأخذ ملخص التوقع وتعطي ترتيب المحاصيل. حالياً قاعدة واحدة أولية (ملاءمة الحرارة المتوقعة)، وهنا تُضاف قواعد الفريق.

**ما نحتاجه من فريق النموذج لإكمال الربط:**

- ملفات النماذج وصيغتها (XGBoost JSON/UBJ، LightGBM، أو joblib) وإصدارات المكتبات.
- لكل نموذج: الهدف، نوع التوقع، الأفق، وأسماء الخصائص **بترتيبها**.
- كود هندسة الخصائص المستخدم في التدريب، ليُنفَّذ في `build_features`.
- مخطط أعمدة قاعدة البيانات وخريطة النقاط الشبكية الـ835.
- شكل المخرجات: قيمة يومية أم إجمالية، والوحدات.
- مقاييس التقييم لكل نموذج (لا تُكتب هنا أرقام غير مقيسة).

بعدها يبقى مكانان فيهما `TODO(model delivery)`: `build_features` وتشغيل الاستدلال في `ProductionPredictionService.predict`.

## الأمان

- كلمات المرور مشفّرة بـ argon2، والجلسات JWT.
- كل طلب على بيانات مستخدم يتحقق من الملكية؛ بيانات غيرك ترجع 404.
- تحديد عدد المحاولات على الدخول والتسجيل وواجهة الضيف.
- التحقق من كل المدخلات في الخادم، ومن هندسة القطع (داخل الأردن، بلا تقاطع ذاتي، رقم غير مكرر).
- لا أسرار في الكود؛ كلها من `.env`.

- ترحيلات قاعدة البيانات: الجداول تُنشأ عند التشغيل، وتغيير المخطط يحتاج حذف `ardna.db`.
- تحديد الطلبات في الذاكرة، ويكفي لخادم واحد فقط.
